## 保留的七项运营优化

用户要求上一轮列出的七项优化全部实现。本轮只使用临时 Profile、SQLite、模拟网页/执行器和本地图片，没有新发布、评论、私信、回关或外部模型调用，没有使用 computer use，也没有重启用户 Server。

1. **人工核对保留证据**：`action_history.py` 追加人工结论与修改前回执，原链接和自动核对事实保留；操作者标为“本机操作员”。人工与自动结论分别展示，日报区分证据来源。读任务携带结果版本指纹，迟到结果不能覆盖人工决定。
2. **持续审核跟踪**：`review_queue.py` 将 tracking 保存在现有 objects，复用 Desktop commands 和原 Cron；审核中退避到一小时，最多跟踪七天；网络/不明确结果自动八次后转人工，内容不一致/审核拒绝停止自动复查。私有 check 接口幂等，展示下次时间、排队/检查状态，平台通过或拒绝产生应用内通知。
3. **提交与核对超时拆分**：`browser.ts` 提交回执后返回 submitted；`Store.acknowledge` 原子保存回执并创建独立 verify 命令（180 秒，提交仍 120 秒）。恢复只入队读取，不重发。`late_receipts.py` 接受仍属于本次未决动作的迟到发布回执，拒绝覆盖新尝试或人工结果；重复回执幂等。已开始步骤可补记迟到结束证据，禁止到期后开始新步骤。
4. **最终稿快照**：`publication_snapshot.py` 与动作/命令同事务保存内容、图片顺序、来源元数据、账号及完整规则版本，重试另存快照。快照图片受本动作素材范围约束，读取时校验原文件哈希，后改资料不改变既定稿件。
5. **异常处理入口**：`action_details.py` / `action-inspector.tsx` 提供分类说明、只读立即核对、登录入口、批准稿与实际文本对比、人工历史、诊断 ZIP。图片在展开快照后才加载。页面请求随 Profile 切换隔离并忽略迟到响应。
6. **图片辅助核对**：`image_comparison.py` 比较尺寸、解码后像素和缩略图相似度，显示原图和平台参考图。两张并发、逐张释放原始大图，辅助解码上限 1600 万像素。仅相似或像素相同都不升级自动精确匹配；仍以授权文件 SHA-256 一致为自动依据。
7. **证据容量管理**：`evidence_storage.py` / `evidence-storage.tsx` 显示占用与可复用页，配置 7～365 天（默认 30 天、自动清理关闭），支持手动/每日清理。未解决异常、最终稿、人工结论与仍被引用截图保留。诊断 ZIP 为本动作无截断 JSON 与说明，去除密钥类字段和 URL 查询参数，不附图片文件。

没有新增公共 API、核心工具、常驻调度器或 SQL 表。私有接口集中在 `dashboard/browser_api.py`，步骤/截图/快照/跟踪均复用 events、objects、commands、actions。

## 使用与剩余边界

- 重启 Server 加载新 Python 接口；开发 Desktop 可 HMR，发布包需重建。入口：运营管理 → 任务与执行 → 动作详情 / 日志与截图存储管理。
- 未取得明确审核状态、转码或图片过大时仍保留待确认/核对不完整；相似度不是自动成功依据。日报保留生成时的事实快照，后到核对结果在动作台账。
- 核对仍需启用规则、无人工接管、正确登录账号及 Desktop 在线；“立即核对”不绕过这些前提。七天/八次结束后可人工处理或手动只读检查。

- 应用内通知按当前挂载执行器去重；重新打开执行器可能再次提示最近状态。
