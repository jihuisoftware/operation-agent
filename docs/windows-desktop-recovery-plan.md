# Windows 桌面版本恢复计划

- 制定日期：2026-11-11
- 源码评估基准：`51ff94905f`
- 状态：源码与本地契约恢复已实施；Windows 原生构建、安装、签名及升级验收待完成（更新于 2026-11-12）
- 目标：在保留现有 macOS 能力和运营修复的基础上，恢复可安装、运行、更新及卸载的 Windows 桌面应用。

## 1. 第一阶段交付范围

| 项目 | 默认范围 |
| --- | --- |
| 操作系统 | Windows 11 x64；具体最低系统构建号在原生环境验收后写入支持声明 |
| 应用形态 | Electron 桌面应用，简体中文 |
| 安装包 | `bundled` 完整包，包含本地 Python 后台、锁定依赖和所需托管工具 |
| 安装与更新 | 优先恢复已有 MSIX / AppInstaller 路线，暂按用户确认复用原发行身份与更新配置，后续替换为本项目配置 |
| 业务能力 | 资料采集整理、分析、写稿、封面与组图、审核排期、执行记录，以及当前已开放的平台操作 |
| 后台结构 | 沿用统一 Gateway、`state/` 和现有插件，不另建 Windows 专用业务后端 |
| macOS | 持续支持，所有平台分支恢复须通过 macOS 回归 |

本轮不恢复终端聊天 UI、Linux 桌面发行、Docker 镜像发行、消息平台适配器或已关闭的工具。Windows ARM64、Microsoft Store、轻量远程客户端和独立安装引导器单独排期。

“能启动开发版”“能安装测试包”“可正式分发”是三个独立里程碑。未完成原生验收前，不在 README 宣称 Windows 已受支持。

## 2. 当前基础与缺口

| 区域 | 当前证据 | 恢复工作 |
| --- | --- | --- |
| 界面与业务 | Electron、React、运营插件及 Python 后台主体仍在 | 复用实现，核对平台差异 |
| 启动和构建准入 | `platform-policy.cjs` 拒绝非 macOS；入口、构建及打包都会调用 | 改为明确的受支持平台规则，并统一消费者 |
| 完整包目标 | `desktop_prepare.py` 仅接受 Darwin 两种架构 | 增加 Windows x64，并验证整套原生载荷 |
| Windows 基础能力 | 保留 `gateway_windows.py`、部分 Windows 更新、SSH 等模块 | 审查仍有消费者的实现与调用契约 |
| 工具版本 | `pm/lock.json` 保留 Windows 目标 | 验证下载、完整性、解压和可执行文件解析 |
| 安装与发布 | PowerShell 安装脚本、部分任务已移除；仍有 MSIX 代码与配置残留 | 从历史按需恢复，贯通构建、签名、产物与更新通道 |

只恢复需要的文件、函数和配置；不整体回退此前精简提交。尤其不能撤销统一 Gateway、`state/` 迁移、发布防重、批次阻塞隔离和人工内容原位编辑。

## 3. 阶段一：盘点与冻结恢复边界

### 工作

1. 对照 Git 历史，建立 Windows 文件清单：保留、删除、替换、失去消费者四类。
2. 检查启动、打包、安装、更新、卸载链路的每个入口，区分仍工作的实现和仅有名称的历史残留。
3. 在 Windows 11 x64 测试机或原生 Windows CI 上固定验证环境，包括路径、系统版本、架构与工具版本。
4. 评估现有 MSIX/AppInstaller 链路的可恢复性。若发现无法继续使用的关键依赖，先记录阻碍，再单独评审安装格式变更，不并行维护两套安装器。
5. 确定本项目 Windows 包身份、可执行文件名、协议名称及更新来源；核对用户数据归属，避免误连接上游发行通道。

## 4. 阶段二：恢复 Windows 开发运行

### 工作

1. 将平台策略改为明确支持 macOS 与 Windows；同步 Electron 入口、构建脚本、打包脚本和相关声明与测试。Linux 等其他目标仍拒绝。
2. 恢复 Windows 开发启动命令，避免依赖 Bash、macOS 工具或开发机固定路径。
3. 验证 PM 在 Windows 上解析 Python、Node、npm、Git 等工具；所有可执行文件查找仍通过现有平台解析层。
4. 贯通 `hermes gateway ensure`、连接票据、WebSocket、私有 HTTP 接口，以及停止、重启和重复启动的进程识别。
5. 验证路径包含空格、中文用户名、不同磁盘及多个 Profile；不把运行数据写入安装包目录。

### 完成条件

Windows 上能启动 Desktop 与 Gateway，完成模型配置、对话、工具调用和会话保存；重启后可以恢复记录。不能通过关闭鉴权或绕过 Profile 隔离来通过验收。

## 5. 阶段三：运营能力与系统差异适配

| 场景 | 检查与修复内容 |
| --- | --- |
| 采集与分析 | 网络请求、代理、超时、文件编码、模型调用及缓存复用 |
| 编辑器 | 中文输入法组合输入、快捷键、复制粘贴、图片拖放、本地保存与冲突处理 |
| 本地封面 | Windows 中文字体、字体集合索引、文字测量、PNG 输出；字体缺失应有明确提示 |
| 文件与素材 | 中文文件名、授权素材读取、上传、导出、临时文件和文件占用 |
| 网页执行器 | webview 创建、登录分区持久化、导航、文件上传、执行心跳及崩溃恢复 |
| 审核与排期 | 到期派发、离线原因展示、新任务账号重验、原位编辑后重新审核、防重复提交 |
| 睡眠与唤醒 | 实际睡眠、锁屏、唤醒、账号只读重验、保持唤醒设置及旧命令取消 |
| 退出与后台 | 关闭窗口、退出应用、停止后台、子进程回收、文件锁释放及重新启动 |
| 插件兼容 | 用实际执行宿主判断后台插件平台兼容性；远程后台与桌面所在系统分开处理 |

睡眠与锁屏不能当作同一个事件；不得通过模拟 `sys.platform` 宣称已完成 Windows 验证。平台发布默认使用隔离数据和模拟执行器，真实账号验收先限定为登录与只读检查。

### 完成条件

核心运营链路在 Windows 原生环境中通过；故障可见、数据可恢复，没有重复发送、跨 Profile 数据混用或退出后的失控执行。

## 6. 阶段四：恢复完整安装包

### 工作

1. 在 Windows 原生构建环境准备 x64 Python、依赖、托管工具及 Electron 资源；检查原生扩展架构一致性。
2. 恢复必要的安装、载荷解包和启动逻辑。历史 PowerShell 脚本必须重新适配现有 PM 与 Gateway，不能原样拿回即视为可用。
3. 配置完整包资源、图标、应用与包身份、版本、安装路径、协议注册和卸载行为。
4. 普通用户首次安装不应手动安装 Python、Node、Git 或运行开发命令；模型和业务账号仍由用户自行配置。
5. 安装包不得包含开发数据库、API Key、网站登录态、本机打包配置或私钥。
6. 先输出隔离测试产物，不上传正式更新通道；明确记录测试包的证书与安装前提。

### 完成条件

在没有开发环境的干净 Windows 机器上，可以安装、启动、退出、重开、卸载。用户数据位于独立可写目录，卸载的数据保留策略明确且已验证。

## 7. 阶段五：签名、更新与发布验收

### 工作

1. 准备与包身份匹配的 Windows 分发签名方案；macOS 证书不能代替 Windows 签名。凭据通过安全存储注入，不提交仓库。
2. 恢复 Windows 发布 lane、产物校验、版本映射、更新元数据、签名检查和验收回执。
3. 使用本项目独立的测试更新通道验证 A → B 升级，确保应用包、后台代码与托管依赖一致。
4. 验证应用正在运行、后台有任务、文件被占用、下载中断、更新失败等情况；失败后应保留可启动版本和用户数据。
5. 验证拒绝未经验证的更新产物，以及现有版本/数据库降级保护。回滚应用不能静默回退不兼容的数据结构。
6. Windows 发布失败不得影响 macOS 已验证的发行与更新通道。

### 完成条件

安装包身份与签名检查通过，干净安装和更新验收均通过，发布门槛与产物来源可追溯，之后才开放 Windows 正式下载。

## 8. 验证矩阵

| 维度 | 必须覆盖 |
| --- | --- |
| 原生宿主 | Windows 11 x64；macOS 现有目标回归 |
| 用户与目录 | 普通用户、中文用户名、含空格路径、独立数据目录、多 Profile |
| 安装形态 | 源码开发、干净完整包安装、覆盖升级、卸载及重装 |
| 网络 | 正常网络、慢代理、断网与恢复 |
| 执行生命周期 | 重复启动、后台重启、任务执行中退出、网页崩溃、真实睡眠与唤醒 |
| 内容发布 | 离线等待、账号恢复、新旧批次隔离、编辑后重审、结果未知不重发 |
| 编辑与素材 | 中文输入、自动保存、正文与封面原位更新、图片上传与导出 |
| 数据安全 | Profile 隔离、权限校验、凭据不入包、更新失败保留数据 |

Python 回归统一通过 `scripts/run_tests.sh`；Windows 原生执行方式在阶段二确定并纳入 CI，保留其环境清理和测试隔离约束。Desktop 运行类型检查、UI 测试、Electron 测试及安装包验收。仓库检查使用 `python scripts/check`。

每个阶段只扩大与本次变更有关的测试范围；先修复本阶段失败，再进入下一阶段。不能用 macOS 上的测试通过代替 Windows 原生结果。

## 9. 建议提交顺序

1. 平台范围与开发入口恢复。
2. Windows Gateway、路径、字体、进程生命周期适配。
3. Windows 运营功能回归与问题修复。
4. 完整包构建、安装及卸载。
5. 签名、更新通道与原生 CI。
6. 完成验收后更新用户说明和下载入口。

各提交保留 macOS 现有行为；通过显式目标选择恢复 Windows，不把已退役能力随着旧文件重新启用。

## 10. 执行前置条件与边界

- 需要可用的 Windows 11 x64 原生测试环境，以及相应 CI runner。
- 正式分发前需要确定 Windows 包身份、签名方案和独立更新地址；开发阶段可以先验证运行和隔离测试包。
- 本计划不要求立即购买证书、安装软件、恢复历史文件或发布产物。
- 当前仅完成源码评估，尚未在 Windows 构建或运行，暂不给出未经实机验证的确定工期。
- 每次启动或重启后台前，必须在相同环境与数据归属下先执行 Gateway stop，等待结束后再启动。
- 默认不清除生产历史阻塞、不重跑生产任务、不发布内容。需要真实提交验收时，另行明确账号、稿件及范围。


## 11. 当前实施进度（2026-11-12）

已实现：Windows x64 开发/构建准入，MSIX 清单与管理命令入口，固定工具准备与校验、原有签名接口和更新重启等待资源，完整测试包 PowerShell 入口，单包 AppInstaller 本地生成，Windows 字体查找、按实际宿主筛选插件，以及手动触发的原生 CI 与隔离启动检查。使用方法见 [Windows 开发与测试包](windows-development.md)。

本机验证只覆盖跨平台契约与 macOS 回归；未把 Windows 原生用例的跳过当作通过。用户确认暂复用旧配置，但没有提供可连接的 Windows 测试机或签名成功证据。本轮未提交或推送源码、未触发远程 CI、未上传安装包、未推进正式更新渠道。阶段四和五仍需原生环境完成安装、签名和 A/B 升级验收，正式发布矩阵保持原状。
