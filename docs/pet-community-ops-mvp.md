# 宠物内容与社群增长 Agent：MVP 方案

日期：2026-10-25（Asia/Shanghai）

状态：开发方案；本文中的业务模块、命令和接口均为拟实现内容。

Hermes 参考提交：`4ea8d23cc9`。

## 1. 已确认的业务方向

- 已有宠物社区 App，目前停止运营。
- 当前运营阵地为公众号、小红书、抖音。
- 近期目标是在这些平台建立内容品牌、获得关注并形成持续互动。
- 关注和社区发展达到适当水平后，再评估恢复 App 运营。
- 本阶段优先建设素材、选题、内容生产、审核发布协作、互动整理和增长复盘。
- 主要操作入口已确定为 Hermes Desktop；浏览器 Dashboard 前端与入口移除，Desktop/TUI 共享后端保留。

以下是第一版的设计假设，不代表已经确认的经营数据：由一个内部运营团队使用；每个平台先支持一个账号；从一个固定栏目开始；平台数据可人工导入；尚无自动发布权限的渠道采用发布包导出和人工回填。

品牌名称、目标宠物人群、素材储备、账号现状和可投入人力仍待运营配置。缺少这些信息时，系统应提示资料缺口，不自行编造品牌事实或历史成绩。

## 2. 第一版的完成定义

一个固定栏目可以连续完成：

```text
有来源和使用范围的素材
  → 有依据的选题
  → 公众号／小红书／抖音内容变体
  → 分平台审核
  → 发布包导出或已授权渠道执行
  → 发布结果核对
  → 互动和指标回收
  → 下一期选题调整
```

第一版交付的是可重复执行的运营流程。发文数量和粉丝增长属于需要通过真实运营验证的结果，不作为系统能够保证的产出。

首个栏目可采用“我家宠物的小习惯”，仅作为可替换的演示案例。系统从同一份真实故事生成图文、短视频脚本和完整文章；脚本、成片和已发布内容分别记录，不将脚本完成标为视频制作完成。

## 3. 范围和阶段

| 阶段 | 交付 | 验收依据 |
| --- | --- | --- |
| M1：素材到内容包 | 品牌配置、素材登记、选题、三个平台变体、版本审核、导出 | 一组获授权素材生成完整内容包，来源和版本可追溯 |
| M2：发布与互动台账 | 排期、人工发布回填、发布结果核对、评论导入、回复建议 | 每次发布和互动处理都有明确状态；重试不会盲目重复执行 |
| M3：增长复盘 | 指标导入、数据口径、栏目比较、下一期计划 | 同一份数据重复导入结果一致；缺失值不被当成零；建议引用证据 |

M1 至 M3 共同构成 MVP。外部账号执行必须使用实际授权和已确认可用的渠道能力；MVP 可完全通过人工发布和后台数据导入完成验收。

后续按真实需求增加自动发布、自动获取数据、有限自动回复和界面扩展。App 数据接口、站内推荐、用户召回、App 推送、模型训练、多企业 SaaS、广告投放和批量私信不进入本阶段。

## 4. 内容与社群策略

| 平台 | 初始分工（待数据验证） | 内容包字段 |
| --- | --- | --- |
| 公众号 | 完整故事、主题合集、精选投稿、活动回顾 | 标题、摘要、正文、封面、配图位置和说明、来源 |
| 小红书 | 宠物日常、成长记录、具体场景、讨论话题 | 标题备选、封面文案、逐页图文、正文、话题建议、来源 |
| 抖音 | 宠物故事、现场互动、连续记录 | 开场、分镜、素材引用、口播、字幕、剪辑说明、发布文案 |

优先在素材最充分的平台验证栏目，其余平台复用事实和素材并调整表达。平台分工不等于对算法效果的承诺。

互动处理先覆盖常见问题、故事投稿、活动咨询、产品建议和待人工处理事项。回复建议与已发送回复分开记录。未经配置授权，不自动联系用户、征集私密资料或发送消息。

真实经历、采访、产品体验、测试结果必须有来源。没有素材时生成拍摄清单或采访提纲，不生成伪装成真实用户经历的内容。疾病、用药等选题标为需要专业审核。素材来源及用户投稿属于待处理数据，不能改变工具权限和审核规则。

## 5. 技术落点

采用一个运营主 Agent、平台技能和一个独立业务插件包。优先通过现有扩展接口实现；业务集成不写入 Hermes 核心，平台对接适配器随插件维护。

| 部件 | 职责 | 现有接入点 |
| --- | --- | --- |
| 运营主 Agent | 理解目标、提出选题、编排任务、解释复盘 | `AIAgent` 与现有会话流程 |
| 技能包 | 选题、三平台写作、互动归类、复盘 SOP | 插件技能注册机制 |
| 业务插件 | 状态转换、版本、审核、统计、连接器、回执 | `PluginContext.register_tool`、`register_cli_command` |
| 插件存储 | 运营过程的业务事实与事件记录 | `plugins.plugin_storage.plugin_data_dir` / `plugin_db` |
| Kanban | 长任务、人员待办、失败跟进 | 现有任务生命周期，关联业务对象 ID |
| Cron | 到期检查、数据回收提醒、定时复盘 | 现有调度器；不在插件中再建常驻轮询线程 |
| 界面 | 后续展示素材、内容日历、审核和复盘 | Hermes Desktop 与 Desktop Plugin SDK |

业务状态以插件数据库为准，Kanban 引用业务对象并承载待办，避免维护两套相互冲突的发布状态。跨系统同步通过持久化事件重试和核对完成，不将多个系统的写入视为一个事务。

业务数据按宿主 Profile 隔离；密钥使用宿主凭证机制；行为配置使用 `config.yaml` 中的插件配置。新增技能、工具和提示词遵守下一会话生效的缓存约束。无需修改核心工具集合，也不读取已停运 App 的数据库作为启动前提。

第一阶段使用 Desktop 聊天和内容包验证流程，工作台页面在流程稳定后通过 Desktop Plugin SDK 增加。CLI 作为开发、自动化和诊断的辅助入口，暂定插件命令 `hermes pet-ops`，具体子命令在实现时注册；本文不表示这些命令已经存在。共享 `apps/shared`、`tui_gateway`、Gateway 和 `hermes_cli/web_server*` API 后端继续服务 Desktop，不随浏览器前端移除。

## 6. 最小数据模型

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| BrandProfile | 品牌名称、受众、语气、内容方向、事实资料、待补信息 | 未确认字段保持未知；变更记录版本 |
| ChannelAccount | 平台、账号标识、能力状态、授权引用 | 不保存明文凭证；能力按账号确认 |
| Asset | 文件引用、哈希、来源、所有者、使用范围、证明引用、撤回状态 | 私域可见不等于允许公开发布；内容引用具体素材版本 |
| Topic | 栏目、主题、目标受众、依据、素材引用、计划周期 | 无依据的创意标为待验证假设 |
| ContentRevision | 选题、平台、账号、正文／分镜、素材引用、版本、内容哈希 | 已提交审核的版本不可原地覆盖 |
| Approval | 审核人、决定、变体版本、动作范围、账号、有效期 | 不能由模型自行生成有效人工审批 |
| Publication | 变体版本、账号、排期、审批引用、状态、外部 ID／链接 | 每个平台独立记录；重试沿用同一业务动作标识 |
| ExecutionAttempt | 发布记录、尝试序号、请求标识、时间、结果、回执、错误 | 尝试记录追加保存；超时结果不确定时进入核对 |
| Interaction | 平台、内容引用、平台内标识、原文引用、分类、处理状态 | 不基于昵称匹配跨平台身份；外发回复另有动作记录 |
| MetricSnapshot | 平台、账号／内容、统计区间、采集时间、时区、指标名、口径、数值、来源 | 区分缺失与零；保留导入批次和原始口径 |
| Review | 周期、引用快照、结论、假设、后续任务 | 确定事实与待验证建议分别呈现 |

数据库物理拆表以实现时的具体查询和事务需求为准。所有对象使用稳定 ID；时刻统一存储，界面按配置时区展示，默认运营时区为 `Asia/Shanghai`。

## 7. 审核、排期和结果核对

内容版本的流程：`draft → in_review → approved / changes_requested`。需要修改时创建新版本，旧审核记录保留但不授权新版本。

发布记录的流程：

```text
planned → ready → executing → submitted → published
                    │             └────→ failed
                    ├────────────→ failed
                    └────────────→ unknown → reconciling
人工发布：ready → awaiting_manual → submitted / published / unknown
核对结果：reconciling → published / submitted / confirmed_not_published / unknown
```

- 同一主题的三个平台变体分别审核；正文、素材或账号变更后，必须获得覆盖新版本的审核。
- 审核记录明确是否授权直接执行、具体时间或允许的排期窗口。超出范围的时间调整重新审核。
- `submitted` 仅表示平台已接收或仍在审核，不代表对外可见；`published` 需外部状态、有效链接或人工核对证据支持。
- 业务动作以发布记录 ID 标识，调用方重试必须复用该 ID；平台支持幂等键时同步传入。新建发布记录不自动获得“重复发布”授权。
- 请求超时且无法确定结果时标为 `unknown`，先查询或人工核对；确认未发布且错误可重试、授权仍有效时才再次执行。不能保证外部平台的 exactly-once。
- 执行前重新核对当前版本、审批有效性、素材授权和账号能力。素材授权撤回后停止使用该素材的待发布任务，已发布内容生成撤下跟进任务；不宣称已自动完成平台撤回。
- 重启后从持久化记录恢复待办；处于 `executing` 但没有确定结果的任务先核对，不直接重发。
- 待执行任务可取消；执行开始后的取消先核实实际状态。每次状态转换保留操作者、时间和依据。

## 8. 渠道能力与人工路径

连接器按账号声明独立能力：素材上传、创建草稿、提交发布、查询发布状态、读取指标、读取互动、发送回复。能力状态包含 `unknown`、`manual`、`available` 和 `unavailable`，不能因平台名称就默认开放。

第一版三个渠道都必须支持内容包导出。人工回填包括外部链接／ID、实际发布时间、操作者、确认状态和证据；平台数据支持后台文件导入和手工记录。

权限开通、授权有效期、实际接口覆盖范围，在连接账号时逐项核验。接口返回的过期或撤销状态使对应动作停止并进入待处理。本文不承诺任何账号当前具备自动发布、评论管理或数据读取能力。

## 9. 指标与复盘口径

第一版追踪以下维度，但只展示实际获取到的数据：

| 维度 | 指标示例 | 解释边界 |
| --- | --- | --- |
| 内容生产 | 草稿采用率、修改次数、单篇制作时间、模型调用成本 | 原始记录支持，时间未知时不估作实测值 |
| 平台增长 | 净增关注、内容带来的新增关注、主页访问 | 净增关注与新增关注不同；账号增长不直接归因到某篇内容 |
| 内容互动 | 评论、收藏、分享、观看／阅读 | 保留各平台定义；不将不同分母的比率直接排名 |
| 社区参与 | 重复参与、主动投稿、活动参与 | 缺少稳定标识时不推断独立参与人数 |
| 需求信号 | 反复出现的问题、未满足需求、自愿试用意向 | 区分口头意向、报名、真实使用和复访 |

- 缺失数值存为空并记录原因，不能补为零；分母缺失或为零时不输出转化率。
- 对内容设置固定的发布后观察窗口，未满窗口的标记为未成熟；不同窗口不直接比较。
- 账号级周期指标与单篇累计指标分别保存。相同导入批次重复执行不重复计数；修订数据保留来源和修订时间。
- 三平台关注数分别报告，合计只能标为账号关注关系数，不能称为去重用户数。
- 只能在实际可观察的平台和时间范围内计算重复参与；不通过相同昵称拼接用户身份。
- 复盘列出数据依据、资料缺口、候选解释和下一次验证动作。样本少或存在节假日、活动等变化时，不直接给出因果结论。

## 10. App 重启的决策依据

保留用户提出的关注规模目标，同时形成一张“重启证据表”：目标受众的持续参与、主动投稿、现有平台未满足的需求、自愿内测意向、小规模试用后的复访、持续运营成本。

目标关注量、观察周期、内测人数、激活和复访阈值在获得基线后由负责人事先设定，Agent 不自行决定或事后调整标准。平台上的留言与报名不能替代真实试用证据。无需在冷启动阶段要求用户迁移或提供联系方式。

重启评估由人作出，Agent 提供证据和不确定性。App 开发与数据接入作为独立后续项目启动。

## 11. 开发任务与验收

| 顺序 | 开发任务 | 验收 |
| --- | --- | --- |
| 1 | 独立插件骨架、Profile 内存储、配置和 CLI | 两个临时 Profile 的素材、内容和账号状态互不混用 |
| 2 | 素材登记、授权状态和选题 | 未确认公开使用范围的素材可以登记，但不能进入对外发布 |
| 3 | 三平台内容包、版本和审核 | 一个选题关联三个独立变体；修改已审核内容会产生新版本 |
| 4 | 导出、排期、人工回填、执行记录 | 一个平台完成发布不误标其他平台完成；任务重启后可恢复 |
| 5 | 互动和指标导入 | 重复导入不重复计数，缺失值、窗口和来源被正确保留 |
| 6 | 复盘与下一期计划 | 每条数据结论可回溯快照，未知部分明确列出 |
| 7 | 按真实权限增加一个渠道执行能力 | 使用测试替身覆盖超时核对、授权失效和重复触发；真实账号验证另行进行 |

关键行为测试包括：审批版本不匹配拒绝执行；素材撤回阻止待发布；未知结果不会直接重试；同一动作重复触发不会并行发布；平台接收与实际发布状态不同；指标缺失不变成零；跨 Profile 数据隔离；重新启动后核对未完成动作。

测试使用真实插件加载和临时 `HERMES_HOME`，通过 `scripts/run_tests.sh` 执行适用测试；外部平台使用可控测试替身。若源码位于独立插件仓库，其测试命令需在仓库开发指南中单独确定，并补充宿主集成验证。

完成 MVP 时应交付一套可重复演示的数据和操作说明：登记一组样例素材，生成同一栏目三个渠道的内容包，完成分平台审核，导出并模拟回填发布结果，导入互动与指标，再生成下一期计划。演示数据明确标为样例，不混入真实运营成绩。
